# AI Coding Playbook

把 AI 编码从“生成一段代码”推进到“可验证、可审查、可维护的软件交付”。

这个仓库沉淀 AI 原生软件工程中的基础约定：如何描述任务、提供有效上下文、限制变更范围、验证结果，以及由人承担最终工程判断。

> 本仓库提供通用方法和模板，不替代架构设计、安全审查、测试策略或人工代码评审。

## 适用对象

- 希望把 AI 编码纳入日常工程协作的开发者和技术负责人。
- 需要将需求、上下文、验证和审查明确成可执行约定的项目团队。
- 希望从模板开始建立 AI 原生研发工作流的个人开发者。

## 快速开始

1. 从 [任务契约](templates/task-contract.md) 开始，而不是直接要求 AI 修改代码。
2. 在任务中写清目标、非目标、约束、影响范围、验收标准和不可触碰的边界。
3. 按 [工程闭环](docs/engineering-loop.md) 执行：理解 -> 计划 -> 实现 -> 验证 -> 审查 -> 记录。
4. 使用 [审查清单](templates/review-checklist.md) 检查正确性、回归风险、安全和可维护性。

## 核心原则

| 原则 | 含义 |
| --- | --- |
| 先定义，再生成 | 先写任务契约与验收，再让 AI 开始编码。 |
| 上下文最小充分 | 提供完成任务所需的代码、约定和约束，不用无关材料淹没模型。 |
| 变更可控 | 一次只解决一个明确问题；避免顺手重构和大范围改动。 |
| 验证优先 | 测试、类型检查、构建和人工审查是交付的一部分。 |
| 人负责决策 | AI 可以起草、搜索和执行，人对需求、架构、风险和合并负责。 |

## 使用边界

- 不提交密钥、客户资料、内部日志、私有代码或生产数据给不具备授权边界的工具。
- 高风险变更必须增加人工审查、回滚方案和针对性验证。
- 不因生成速度快而跳过测试、代码审查或变更记录。
- 示例不代表任何特定团队、产品或项目的实践结果。
